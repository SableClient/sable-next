# Self-hosted Sable server

Server mode runs Sable and its Matrix stores on your machine. The server holds
your encryption keys and can read plaintext while it is running. Protect the
host and data directory.

## Docker

Pull the image after a release:

```sh
docker pull git.sable.moe/sableclient/sable-next-server:latest
```

Or build it from the repository root:

```sh
docker build -f packaging/server/Dockerfile -t sable-server .
```

The release image has `latest`, full version and major.minor tags. Nightly
images use `dev` and a short commit SHA. The examples below use the published
image; replace its name with `sable-server` if you built it locally.

Generate an Argon2id hash, then create a data directory writable by UID 10001:

```sh
docker run --rm -it git.sable.moe/sableclient/sable-next-server:latest hash-password
```

Start the server:

```sh
mkdir -p sable-server-data
sudo chown 10001:10001 sable-server-data
docker run -d --name sable-server --restart unless-stopped \
  -p 127.0.0.1:18008:18008 \
  -v "$PWD/sable-server-data:/var/lib/sable" \
  -e SABLE_SERVER_PUBLIC_URL=https://sable.example.org \
  -e SABLE_SERVER_USERNAME=sable \
  -e SABLE_SERVER_PASSWORD_HASH='your Argon2id hash' \
  git.sable.moe/sableclient/sable-next-server:latest
```

Put an HTTPS reverse proxy in front of the server. The session cookie is secure,
so HTTPS is required outside loopback local development. Non-loopback `http`
`public_url` values are rejected because browsers will not keep the login cookie.
Back up the data directory and its parent, which contains the Matrix account
stores. Server mode keeps store keys in owner-only files under
`data_dir/secrets`, so the backup must include that directory.

## Binary

Install the project build tools as described in the [README](../README.md), then
build the frontend and server:

```sh
pnpm install
pnpm run build:server
cargo build --release -p sable-server
target/release/sable-server hash-password
```

Create `sable-server.toml`:

```toml
listen_addr = "127.0.0.1:18008"
public_url = "https://sable.example.org"
data_dir = "./sable-server-data"
username = "sable"
password_hash = "$argon2id$v=19$m=19456,t=2,p=1$..."
frontend_dir = "./dist"
```

Start the server with `target/release/sable-server --config sable-server.toml`.
Without `--config`, it looks for `sable-server.toml` in the working directory.
A configuration file is optional when the required values are supplied through
environment variables.

## Configuration

Environment variables override the corresponding TOML fields. Paths are relative
to the working directory unless absolute.

| Environment variable                 | TOML field              | Default                  | Description                                                                                                   |
| ------------------------------------ | ----------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `SABLE_SERVER_LISTEN_ADDR`           | `listen_addr`           | `127.0.0.1:18008`        | Address and port to listen on. The image sets `0.0.0.0:18008`.                                                |
| `SABLE_SERVER_PUBLIC_URL`            | `public_url`            | `http://127.0.0.1:18008` | Browser-visible origin without a path; HTTP is allowed only for loopback. Set this explicitly behind a proxy. |
| `SABLE_SERVER_CLIENT_IP_SOURCE`      | `client_ip_source`      | `ConnectInfo`            | Source of the client IP for rate limiting.                                                                    |
| `SABLE_SERVER_DATA_DIR`              | `data_dir`              | `sable-server-data`      | Directory for persistent data. The image sets `/var/lib/sable/data`.                                          |
| `SABLE_SERVER_ALLOWED_PRIVATE_CIDRS` | `allowed_private_cidrs` | `[]`                     | Private IP addresses or CIDR ranges that all users may access.                                                |
| `SABLE_SERVER_MAX_ACTIVE_USERS`      | `max_active_users`      | `128`                    | Maximum simultaneously loaded workspaces, including the original account.                                     |
| `SABLE_SERVER_USERNAME`              | `username`              | `sable`                  | Username for server login.                                                                                    |
| `SABLE_SERVER_PASSWORD_HASH`         | `password_hash`         | None                     | Argon2id hash for the original server account, generated by `hash-password`.                                  |
| `SABLE_SERVER_OIDC_ISSUER`           | `oidc_issuer`           | None                     | OpenID Connect issuer URL.                                                                                    |
| `SABLE_SERVER_OIDC_CLIENT_ID`        | `oidc_client_id`        | None                     | OpenID Connect client ID.                                                                                     |
| `SABLE_SERVER_OIDC_CLIENT_SECRET`    | `oidc_client_secret`    | None                     | OpenID Connect client secret.                                                                                 |
| `SABLE_SERVER_OIDC_AUTO_PROVISION`   | `oidc_auto_provision`   | `false`                  | Create a user on their first successful OIDC login.                                                           |
| `SABLE_SERVER_FRONTEND_DIR`          | `frontend_dir`          | `dist`                   | Directory containing the server-mode frontend. The image sets `/srv/sable`.                                   |

If `public_url` is left at its default while `listen_addr` changes, it defaults
to `http://<listen_addr>`. That derived URL is valid only when the listen
address is loopback; set an HTTPS public origin for container and proxy
deployments. Quote the password hash in shell commands: it contains `$`.
Account stores are created alongside `data_dir`, so its parent must also be
writable and included in backups.

In a Compose YAML file, escape each `$` in the password hash as `$$` to prevent
variable interpolation, even when the value is quoted. For example:

```yaml
environment:
  SABLE_SERVER_PASSWORD_HASH: '$$argon2id$$v=19$$m=19456,t=2,p=1$$...'
```

The image health check uses port `18008`; if you change the listening port,
also override the health check. The server exposes `/healthz` for health checks.

## Outbound connections

Matrix connections block private and other non-public network addresses by
default. To use a private homeserver, add its address or CIDR range to
`allowed_private_cidrs`, for example `allowed_private_cidrs = ["192.168.1.10/32"]`.
The environment variable accepts an array:

```sh
SABLE_SERVER_ALLOWED_PRIVATE_CIDRS='["192.168.1.10/32"]'
```

All server users can connect to any port on an allowed address. Only allow
networks and services you trust all users to access.

## Reverse proxy

For example, with Caddy:

```caddyfile
sable.example.org {
    reverse_proxy 127.0.0.1:18008
}
```

`ConnectInfo` uses the direct connection address and ignores forwarded headers.
When a trusted reverse proxy terminates TLS, set `client_ip_source` to the
header source it controls, for example `RightmostXForwardedFor`, and ensure the
proxy supplies that header. Configure `public_url` with the browser-visible
HTTPS origin.

## Server users

The original account keeps its existing Matrix stores. Older server versions can
still use those stores, but do not recognize new users or their stores. Back up
`data_dir` and its parent before upgrading or rolling back.

Add a local user with `sable-server --config sable-server.toml add-user USERNAME`.
The command prompts for a password and prints the user ID. Use `list-users`,
`disable-user USER_ID`, `enable-user USER_ID`, and `set-user-password USER_ID`
to manage accounts. Disabling a user blocks new requests and closes active
sessions. To remove a user, stop the server and run `remove-user USER_ID`; add
`--delete-data` to delete their Matrix stores and keys. Removed OIDC identities
cannot be automatically provisioned again.

For a running Docker container, use `docker exec -it sable-server sable-server
add-user USERNAME` and the same pattern for other online management commands.
For removal, stop the container and run the command in a temporary container
with the same data volume and configuration.

Once loaded, users continue syncing after browsers disconnect, until they are
disabled or the server stops. The server stores each new user's Matrix
credentials and account data under `data_dir/users/USER_ID`. The server
operator can access every user's data. Isolation is enforced within one process,
not by separate operating-system sandboxes.

Browser preferences and notification data, including Matrix access tokens used
for web push, are scoped by account but remain accessible to anyone who controls
the same browser profile. Sable attempts to remove push credentials on logout or
when another server user signs in; browser storage errors may prevent cleanup.
Use separate browser profiles on shared devices. Media requests use the user's
own Matrix account; access to a known media URI is governed by the homeserver's
media policy.

Each user can have up to 16 WebSocket connections, 16 concurrent RPCs, 16
protected HTTP requests, and two uploads. Server-wide limits are 256 connections,
128 RPCs, 128 HTTP requests, four uploads, and eight password checks. Per-user
limits reject excess work; uploads wait for server-wide capacity. Logout remains
available when a user's request limit is reached.

## Server OIDC

Set `oidc_issuer`, `oidc_client_id` and `oidc_client_secret` together, or use
the corresponding environment variables. Register
`https://sable.example.org/_sable/oidc/callback` with the identity provider,
using the configured public origin. The issuer, public origin, authorization
endpoint, token endpoint and signing-key URL require HTTPS except for loopback
development. Create an account for an approved subject with
`sable-server --config sable-server.toml add-oidc-user SUBJECT`. The identity is
bound to the configured issuer and subject; accounts are not linked by email.
To allow first-login account creation, set `oidc_auto_provision = true` (or
`SABLE_SERVER_OIDC_AUTO_PROVISION=true`). Disabled accounts cannot provision
again. The configured legacy password may be omitted for an OIDC-only deployment.
Server OIDC login is separate from Matrix login.

## Matrix OAuth

OAuth login is configured on the Matrix homeserver. The callback returns to the
server UI, so register the browser-visible Sable origin and use that same
origin in `public_url`.

## OIDC integration test

With the Python `cryptography` package installed, run the local mock-provider
check after building the server:

```sh
cargo build -p sable-server
SABLE_TEST_BIN="$PWD/target/debug/sable-server" python3 crates/sable-server/tests/oidc_e2e.py
```

## Upgrade and rollback test

To exercise the legacy store with a previously released server binary, build the
current server and frontend, then run the browser test with the previous binary:

```sh
SABLE_TEST_PREVIOUS_SERVER_BIN=/path/to/previous/sable-server \
  pnpm exec playwright test -c tests/e2e/playwright.ws-server.config.ts \
  -g 'separate server users keep Matrix accounts and media isolated'
```

The test uses temporary data and a local test homeserver.
